# 입력 화면 설계 — 켜고, 넣고, 계산한다

작성 2026-08-24 · 승인 대기

## 1. 무엇을 바꾸는가

지금은 `start.bat` 이 `python src/report.py` 를 먼저 끝까지 돌린 뒤에야 브라우저를
연다. 계산 대상은 코드에 박힌 실험 현장 하나이고, 카메라 후보 100개에 대한 탐욕
선택(경우의 수)까지 매번 돈다. 계산이 실패하면 화면이 아예 안 뜬다.

바꾼 뒤에는 **화면이 먼저 뜨고, 자료를 넣으면 계산한다.**

용도는 **심사 시연**이다. 임의의 현장 도면을 실무로 처리하는 것이 아니라,
"자료를 넣으니 판정이 나온다"는 흐름을 보이는 것이 목표다.

## 2. 실측 근거 — 왜 진단과 재배치를 가르는가

같은 현장(복셀 78,816 · 1m 격자)에서 잰 값이다.

| 경로 | 시간 |
|---|---|
| `site_model.build()` 복셀화 | 0.5초 |
| **진단** — 계획서 카메라 8대만 광선투사 | **7.0초** |
| 재배치 — 카메라 후보 100개 전수 | 약 110초 |

`safety_report.py:70` 이 진단만 하면 되는데도 후보 100개 전부에 광선을 쏜다.
처방 문장(증설·재배치)을 만들기 위해서다. 둘을 가르면 앞쪽이 7초라 진행 바가
필요 없다.

## 3. 구조

`src/serve.py` 를 새로 만든다. 표준 라이브러리 `http.server` 만 쓴다 — 외부 의존 0,
인터넷 요청 0. 지금 `mockup/start.bat` 이 이미 `python -m http.server` 를 띄우고
있으므로 그 자리를 대체하는 것이다.

```
start.bat  →  python src/serve.py  →  브라우저 자동 열림
                                          │
                              ┌───────────┴────────────┐
                              │  [입력] 탭  ← 첫 화면   │
                              └───────────┬────────────┘
                                     [진단 실행]  7초
                                          ▼
                       개요 · 평면도 · 미달구역 · 배치비교 · 기준선
                                          │
                                   [대안 찾기]  ~110초, 진행률
                                          ▼
                                  기하 vs 확률 재배치 비교
```

엔진 모듈(`site_model`·`geometry`·`aggregate`·`optimize`·`prescribe`)은 그대로
import 한다. 계산 로직을 서버에 옮겨 적지 않는다.

### 3.1 API

| 메서드 · 경로 | 하는 일 |
|---|---|
| `GET /` 및 정적 파일 | `mockup/` 을 그대로 서빙 |
| `POST /api/validate` | 입력 검증만. 계산하지 않는다 |
| `POST /api/diagnose` | 진단. 계획서 카메라만 광선투사 |
| `POST /api/optimize` | 재배치. 후보 전수 |
| `GET /api/job/<id>` | 진행 상태 폴링 |
| `GET /api/sample` | `data/` 의 예제 자료 4종을 그대로 반환 |

응답은 지금 `mockup/data.json` 과 **같은 계약**이다. `viewer.js`·`plan.js` 를
건드리지 않기 위해서다.

`POST` 는 job id 를 즉시 반환하고 계산은 워커 스레드에서 돈다. 진행 중에 같은
종류의 요청이 또 오면 **409 로 거절한다** — 버튼을 두 번 눌러 작업이 겹치지 않게.

### 3.2 캐시

입력 JSON 을 정규화해 해시하고, 같은 해시면 재계산 없이 이전 결과를 준다.
같은 시연을 두 번 할 때 7초도 기다리지 않는다.

## 4. 입력 계약

서류로는 **둘**이다 — 설계도면과 안전관리계획서. 계획서 한 권 안에서 세 군데를
쓴다. 조항 대응표는 `docs/reference/입력자료_출처매핑.md` 에 있다.

파일로는 넷이다.

| # | 자료 | 필수 | 없으면 |
|---|---|---|---|
| 1 | 골조 `building.json` | 필수 | 계산 불가 |
| 2 | 위험구역 `zones.json` | 권장 | `zone_derive` 의 T1 구역(슬래브 단부·갱폼 작업면·타설면)만 남고 굴착면·리프트·크레인·야적장이 빠진다 |
| 3 | CCTV 계획 | 필수 | 화면 표에서 직접 입력해도 된다 |
| 4 | 공정 `schedule.json` | 선택 | 시간대별 진단만 비활성 |

### 4.1 카메라는 표가 1급 입력이다

안전관리계획서 매뉴얼(본문 28쪽 3.2.3 나. 6) 가))이 적으라는 것은
**설치위치 · 설치개소 · 장비의 규격** 셋이다. 우리 입력과 이렇게 대응한다.

| 매뉴얼 | 표의 열 |
|---|---|
| 설치위치 | `x`, `y`, `z` |
| 설치개소 | 행 수 |
| 장비의 규격 | `hfov_deg`, `img_w`, `img_h` |
| **(없음)** | **`yaw_deg` — 어디를 보는가** |

**`yaw_deg` 는 서류에 칸이 없다.** 그런데 검출확률은 방위에 지배된다. 그래서
표의 방위 칸은 **비워둘 수 있게** 한다. 비면 `geometry.choose_yaw` 가 위험가중
가시량을 최대로 만드는 방위를 15° 간격으로 고른다.

이것은 **낙관 방향이다** — 실제 계획서의 방위가 그보다 나쁠 수 있는데 최선을
가정하는 것이다. 화면에 「자동 조준(최선 가정)」이라고 표시하고, 보고서에도
그렇게 나가야 한다.

### 4.2 파라미터 폼

지금 `config.py` 하드코딩 중 심사자가 물을 만한 것만 올린다.

| 항목 | 기본값 | 비고 |
|---|---|---|
| 카메라 예산 | 8 | 재배치에만 쓴다 |
| 판정 임계 `P_DETECT_THRESHOLD` | 0.5 | **잠정값**임을 화면에 표시 |
| 목표 커버리지 | 0.90 | KISA 인증 기준을 목표선으로 빌린 것 |
| 비계 시야 점유율 | 0.35 | **근거 없음** · 민감도 스윕 대상 |
| 복셀 격자 | 1 m | 계산 시간을 지배한다 |

### 4.3 화면 제약 (`CLAUDE.md` §7 Phase 4 유지)

입력 탭이 생겨도 이 셋은 그대로다.

- **단일 HTML.** 빌드 스텝·번들러·프레임워크 없음
- **`localStorage` / `sessionStorage` 금지.** 입력값을 기억시키고 싶어지는 자리가
  생기지만 쓰지 않는다. 다시 넣거나 「예제 자료로 채우기」를 쓴다
- 데이터를 HTML 에 하드코딩하지 않는다. 지금 `data.js` 폴백은 `file://` 로 열
  때를 위한 것이며, 서버가 뜨면 API 응답이 이긴다

## 5. 검증

검증을 통과하기 전에는 계산 버튼이 눌리지 않는다. 실패 메시지는 어느 파일 어느
항목인지 그대로 쓴다.

엔진이 이미 던지는 것은 그 메시지를 올린다.

- `storey_levels_m` 과 층고 불일치 (`site_model.py:146`)
- `source` 없는 위험구역 (`site_model.py:210`)
- `zone_derive` 도출 구역과 이름 충돌 (`site_model.py:201`)

새로 볼 것.

- JSON 파싱, 필수 키 존재
- `solids[].box` 가 숫자 6개이고 `x1<x2, y1<y2, z1<z2`
- 카메라 `x,y` 가 현장 범위 안, `z>0`, `0<hfov_deg<180`, `img_w/h>0`
- `yaw_deg` 는 없거나 0~360
- `schedule.windows[].active_zones` 의 이름이 실제 위험구역에 있는지

## 6. 엔진 변경점

새 기능이 아니라, 입력이 바뀔 수 있게 되면서 드러나는 결함을 막는 것이다.

**(가) 현장 크기를 파일에서 읽는다.**
지금은 `config.SITE_WIDTH_M`(100)·`SITE_DEPTH_M`(60) 을 **세 곳**이 각자 읽는다 —
`_cameras`(`site_model.py:253`), `_voxels`(`:357`), `build`(`:410`). 층고는
`building.json` 과 다르면 `raise` 하는데(`:146`) **크기는 다르면 조용히 무시하고
100×60 으로 계산한다.** 입력이 하나뿐인 지금은 안 드러나지만, 자료를 받는
구조에서는 틀린 답을 내는 경로가 된다.

`build()` 가 경로를 인자로 받아 크기·층고를 파일에서 읽고, 그 값을 `_cameras`·
`_voxels` 로 **넘겨준다.** 세 곳이 각자 전역을 읽는 지금 구조로는 파일 값이 두
곳에 안 닿는다. `config` 값은 인자가 없을 때의 기본값 자리로 내린다.

**(나) `plan_io.load()` 가 `yaw_deg` 없는 카메라를 허용한다.**
지금은 `float(c["yaw_deg"])` 로 필수다 (`plan_io.py:41`). 없으면 `fixed_yaws` 에
넣지 않고 `geometry` 의 자동 조준에 맡긴다. §4.1 의 근거다.

**(다) 진단 경로가 후보 전수를 돌지 않는다.**
`safety_report.build()` 를 진단과 처방으로 가른다. 처방(`prescribe`)이 필요할 때만
후보 100개를 붙인다. §2 의 근거다.

## 7. 오류 처리

계산이 실패해도 화면은 산다. 지금 `start.bat` 은 실패 시 브라우저를 안 여는데,
새 구조에서는 화면이 먼저 뜨고 오류가 입력 탭에 나온다.

서버가 죽으면 화면은 마지막 결과를 그대로 들고 있다. 새 계산만 안 될 뿐이다.

## 8. 수용 조건

1. `start.bat` 실행 → 브라우저가 열리고 **입력 탭**이 보인다. 이 시점에 계산은
   한 번도 돌지 않았다.
2. 「예제 자료로 채우기」 → 검증 통과 → 「진단 실행」 → **10초 안에** 결과 탭이
   활성화되고 히트맵이 그려진다.
3. 카메라 표에서 한 대의 좌표를 바꾸고 다시 진단하면 WDR 이 달라진다.
4. 방위 칸을 비우면 결과에 「자동 조준(최선 가정)」이 표시된다.
5. 「대안 찾기」 → 진행률이 오르고, 끝나면 기하·가정·실측 세 배치가 비교된다.
6. 골조 파일에 `storey_levels_m` 을 틀리게 넣으면 계산이 시작되지 않고 입력 탭에
   `site_model` 의 메시지가 그대로 뜬다.
7. 콘솔 경고 0 (`CLAUDE.md` §7 Phase 4 Acceptance 유지).

## 9. 제외

`CLAUDE.md` §6 의 제외 목록에 더해, 이번 작업에서 하지 않는 것.

| 제외 | 사유 |
|---|---|
| DWF·DWG·IFC 파서 | 도면마다 레이어·축척·좌표계가 달라 일반화가 안 된다. 실패하면 시연이 통째로 막힌다 |
| 도면 이미지 축척 정합 | 배경 이미지는 참고용이며 계산에 쓰지 않는다. 화면에 그렇게 표시한다 |
| 화면에서 골조·위험구역 폴리곤 그리기 | 구현량이 가장 크고, 자료를 파일로 받으면 필요 없다 |
| 데이터베이스·사용자 인증·배포 | `CLAUDE.md` §6 유지 |
| 결과의 서버측 영구 저장 | 프로세스가 살아 있는 동안만. 파일로 떨구는 것은 지금처럼 `outputs/` |
