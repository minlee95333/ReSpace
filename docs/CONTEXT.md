## 3. ⚠️ 발견된 위험 — 주차 축 전제가 흔들린다

### 3.1 사실

> **30㎡ 미만 준주택으로 리모델링할 경우 2027년까지 주차장 추가 신설 의무를 한시적으로 면제**
> (주차장법 시행령 개정 — 국토교통부 비아파트 공급 대책)

출처: [뉴시스 2026-05-26](https://www.newsis.com/view/NISX20260526_0003643247) 외 다수 보도

**[미확인] 개정 "추진/계획" 단계 보도다. 실제 시행 여부·시점·적용 범위를 조문에서 확인하지 못했다.**

### 3.2 왜 문제인가

Re:Space 의 핵심 주장은 **평면·주차·정화조 3축 중 무엇이 병목인가**이고,
PRD 2.3절은 *"비주택 용도변경 상담의 70% 이상이 주차와 정화조에서 막힌다"* 로 시작한다.

그런데 설계안 ③ 에서 세대 규격을 **청년 18.0㎡ / 신혼 28.8㎡ — 둘 다 30㎡ 미만**으로 확정했다.
주차 계수 0.5 구간에 넣으려고 신혼형을 30.0㎡ 에서 28.8㎡ 로 줄인 결정이었다.

**그 규격이 면제 대상에 정확히 들어간다.** 면제가 시행되면:

- `caps.py` 의 주차 축(`기존 주차대수 ÷ 평균계수`)이 무의미해진다
- 주차가 병목이 될 수 없다
- 3축 중 1축이 사실상 사라진다

**심사위원이 이 사업 담당자라면 가장 먼저 지적할 지점이다.**

### 3.3 대응 방향 (권장)

위기가 아니라 **소재로 전환한다.**

> "주차 규제가 완화되면 병목이 주차에서 정화조·평면으로 **이동한다.**"

이것은 3축 구조를 가진 도구만 보여줄 수 있는 장면이다. 단일 지표 도구는 규제가 바뀌면
그냥 틀린 답을 낸다. `rules.json` 의 `parking.bands` 만 교체하면 병목이 뒤집히는 것을
실제로 시연할 수 있고, 이는 설계안 2절의 *"기준 개정 시 데이터만 교체"* 주장을 증명한다.

제안서에서 다룰 위치: 2번(현황분석) 또는 3번(개선방안)에 **규제 변동 시나리오**로 편입.

### 4.1 구현 완료 — 검증됨

`python -m unittest` 실행 결과 **131개 테스트 전부 통과** (34초). 의존성 0 (표준 라이브러리만).

| 단계 | 모듈 | 내용 |
|---|---|---|
| ① load | `contracts.py` | 입력 검증 + SHA-256 해시. 600mm 배수 아니면 거부 |
| ② gridify | `grid.py` | 600mm 격자화, 셀 상태 6종 |
| ③ corridor | `corridor.py` | 복도 자동 생성 + 중복도/편복도/불가 자체 판정 |
| ④ reachability | `egress.py` | 4방향 BFS 보행거리. `stair` 코어만 출발점 |
| ⑤ place | `place.py` | 유닛 배치, 3전략. **난수 없음** |
| ⑥ daylight | `daylight.py` | 창면적비 ≥ 바닥면적/10 |
| ⑦ common | `common.py` | 잔여 영역 → 공용시설 (사유별) |
| ⑧ caps | `caps.py` | **3축 상한 + 병목 판정 + 등급** |
| ⑨ emit | `emit.py` | `result.json` + 층별 SVG |

부수 도구: `report.py`(CLI), `inspect.py`(ASCII 평면), `dashboard.py`(자립형 HTML 4화면), `run.bat`

### 4.2 계산되는 값

```
평면   = Σ 층별 배치 세대수
주차   = 기존 주차대수 ÷ 평균 주차계수 (배치된 유형 구성비 반영)
정화조 = 기존 용량(㎥) × 세대/㎥

공급가능 = min(세 축)   /   병목 = 최솟값을 만든 축
```

물량(단가 없음): 신설 벽체 연장, 설비 재사용률, 공용면적, 주차 부족 대수, 정화조 부족 용량
판정 등급: 우선검토 / 조건부 검토 / 검토 가능 / 부적합 — 각각 이유 문자열 자동 생성
재현성: `result.json` 에 입력 4개 파일 SHA-256 + `rules.json` 버전 기록

### 4.3 입력 형식 — CAD 아님

`floor_plan_XX.json` (mm 정수 좌표, 600mm 배수 강제). 층마다 1파일.
들어가는 것: `boundary`(외벽), `cores`(stair/ev 구분), `shafts`, `columns`, `windows`
**내부 벽 정보 없음** → 철거 물량(`demo_wall_m`)은 구조적으로 산출 불가.

DWG 자동 추출은 **의도적으로 제외**했다. `TECH-SPEC.md` 73~75줄:

> DWG 는 비공개 바이너리 포맷이며 국내 도면의 레이어 명명 규칙이 표준화돼 있지 않아
> 자동 추출은 오류 위험이 크다. **사람이 CAD 에서 외벽·코어·창호를 지정해 중간표현으로
> 내보내는 단계를 명시적으로 둔다. 자동화 실패가 아니라 설계 판단이다.**

IFC 도 미구현 — 제안서상 "입력 어댑터" 자리로만 존치.

**CONVERT-GATE 는 20일 안에 불가능하다.** Phase 3(RL 환경)만 해도 학습·비교 실험이 필요하다.
Re:Space 가 RL 을 쓰지 않고 *"최적화가 아니라 규칙 기반 배치"* 로 부르는 것은 후퇴가 아니라
**방어 가능성을 택한 결정**이다 — 심사에서 "왜 RL 이 필요한가"를 방어할 필요가 없어진다.

두 문서가 충돌하므로 **어느 쪽이 살아 있는지 정하고 `dsg/CLAUDE.md` 를 정리해야 한다.**
현재 `dsg/CLAUDE.md` 는 CONVERT-GATE 기준으로 작성돼 있다.
